## P1 優先修正

### R01 新貼文預設共享，與預設私人的規格相反

- 位置：`app/(main)/write/page.tsx:30`、同檔 `:92`；對照 `app/api/posts/route.ts:263`。
- 前端初始 visibility 是 FAMILY，發布會明確送出 FAMILY；後端雖然有 PRIVATE fallback，也不會套用到正常 UI 請求。
- 影響：家人以為在寫私人手札，未改受眾就發布時，內容立即對所有家人開放。
- 建議：若沒有另外核定改需求，將初始值恢復 PRIVATE，編輯既有貼文則保留原受眾；發布前明示誰能看見。
- 驗收：新貼文不選受眾，另一個家庭帳號無法經動態、搜尋或媒體 API 取得；主動選家人後才可見。

### R02 倉庫內 Compose 沒有掛載媒體持久化目錄

- 位置：`compose.yaml:23` 的 web 服務；`app/api/upload/route.ts:70`；`app/api/me/avatar/route.ts:31`；Dockerfile 的 `/data` 建立步驟。
- db 有持久化 volume，web 沒有 volumes；上傳與頭像直接寫入容器的 `/data/media`。
- 影響：若 NAS 照這份 Compose 啟動，重建或移除 web 容器會遺失影音與頭像，DB 卻留下指向不存在檔案的紀錄。單純 restart 尚不足以重現，必須測試 recreate。
- 建議：先檢查實際 NAS mounts。若現有檔案已在容器內，先備份並搬移，再增加持久化掛載；直接掛空目錄會遮住現有檔案。統一使用 MEDIA_ROOT 設定，檢查掛載與可寫性。
- 驗收：隔離環境上傳→記錄 checksum→recreate web→下載仍相同；備份還原同時包含 DB 與原檔。
- 本次不能據此斷言 NAS 已經丟資料，也未確認是否有額外 Compose override。

### R03 首次改密碼只做前端導頁，後端沒有強制限制

- 位置：`lib/auth/middleware.ts:52–66`、`lib/auth/session.ts` 的 createSession、`components/login-form.tsx:50`、`app/(main)/layout.tsx`。
- 登入回 requirePasswordChange 後，只有表單 router 導向改密碼。requireAuth 不檢查 mustChangePassword／restricted，主 layout 也只檢查是否登入。
- 影響：用臨時密碼取得 Cookie 後，可以跳過改密碼頁直接呼叫其他受保護 API 或開啟內容頁。若為管理員臨時帳號，管理 API 也沿用同一個沒有這項限制的入口。
- 隔離重現：實際 middleware 在 mustChangePassword=true、restricted=true 的合成 session 下仍通過。
- 建議：將「已驗證但須改密碼」作為受限狀態，由後端預設拒絕內容與管理操作，只放行必要的自己資訊、改密碼、登出；頁面也導向改密碼。不能只增加 UI 隱藏。
- 驗收：未改密碼時，直接呼叫 feed、media、posts、admin API 均被拒絕；完成修改並換發 session 才放行。

### R04 Vault 改密碼後，既有內容無法用新密碼解密

- 位置：`app/api/vault/pin/route.ts:45–73`、`lib/vault/crypto.ts:8–35`、`app/(main)/vault/list/page.tsx:95–101`。
- PUT 只更新 pinHash；內容加密金鑰直接由 PIN＋salt 推導。資料未重新加密，也沒有獨立資料金鑰的重包裝流程。
- 影響：呼叫改 PIN API 後，新 PIN 可通過登入驗證，但舊文章仍使用舊金鑰加密，重新解鎖後會顯示解密失敗。這不是單純 UI 錯誤。
- 建議：尚未完成安全遷移前，先阻止這個改密碼 API。正式方案可採獨立隨機資料金鑰、密碼衍生包裝金鑰；變更時重新包裝並撤銷舊 Vault session。也可設計完整重新加密，但須具備交易／版本與失敗恢復，不能只更改驗證 hash。
- 驗收：建立多筆內容→換密碼→重開瀏覽器→全部仍可解密；換密碼中斷不造成部分資料永遠失聯。

### R05 Vault schema 已加入，卻沒有對應 migration

- 位置：`prisma/schema.prisma:414–453`；`prisma/migrations/`。
- VaultPin、VaultItem、VaultAttachment 已被 API 使用，六個既有 migration 皆未建立它們。
- 影響：新 NAS 或隔離 DB 只跑 prisma migrate deploy，會缺少這三張表；即使目前某台 DB 用 db push 建過，也不能從 Git 重現或穩定還原。
- 建議：在隔離環境產生／審查非破壞 migration；先檢查現有 DB 是否已有相同表，再規劃漂移校正，不能直接 reset 或盲目重建現有表。
- 驗收：全新空 DB 僅用版本庫 migration 即可建立全部 schema；既有有資料 DB 升級資料不丟失。

### R06 貼文 version 欄位未真正防止跨裝置覆寫

- 位置：`app/api/posts/[id]/route.ts:384`、`:534–536`；`app/(main)/write/[id]/page.tsx`。
- API 讀出原文後設定 `version = existingPost.version + 1`，最後只以 id 更新，沒有要求 expectedVersion 或在 UPDATE 條件中比對版本。
- 影響：兩個分頁開啟同篇後先後儲存，後者可用過時資料覆蓋先存的內容；存在 version 數字不等於有樂觀鎖。schema 也沒有目前規格規劃的 revision 保存。
- 建議：前端傳入來源版本，交易內以 id＋version 原子條件更新，衝突回 409、保留草稿供比較；受眾與媒體修改一起納入，不能只改文字部分。需要可復原時保存版本快照。
- 驗收：兩個相同來源版本的更新至多一個成功；另一個明確衝突，不會靜默覆寫。

### R07 唯一管理員可以把自己降為一般成員

- 位置：`app/api/admin/users/[id]/route.ts:139–148`、`:189`。
- API 允許 role=MEMBER；只能看到禁止停用自己，沒有最後可用管理員檢查，也沒有禁止自我降權的規則。
- 影響：唯一管理員直接 PATCH 自己的角色後，全家失去管理入口，需要本機介入恢復。
- 建議：交易內保證至少一位 ACTIVE ADMIN，鎖定相關狀態以防兩名管理員互相停用／降權的競態；管理操作另加近期重新驗證。
- 驗收：唯一管理員自降權被拒絕；兩名管理員同時操作後仍至少保留一位可用管理員。

## P2 接續處理

### R08 大影片全檔進入記憶體，沒有 Range 或轉碼

- 位置：`app/api/upload/route.ts:84`、`:135`；`app/api/media/[id]/route.ts:76–90`；Dockerfile、compose.yaml。
- 上傳先解析全部 formData，再 arrayBuffer；讀取使用 readFile 後建立新 Uint8Array。單檔允許達 500MB，沒有串流 Range 回應或背景轉碼 worker。
- 影響：多個家人上傳／觀看長片時容易形成高記憶體壓力，進度拖曳無法取得適當的 206 分段回應；接受 MOV／HEIC 等 MIME 不代表瀏覽器可播。
- 建議：分段續傳／串流讀取與 Range；實際檔頭及 ffprobe 辨識；配額、暫存清理；獨立背景轉碼，先保留原檔，再逐項驗證格式矩陣。
- 驗收：記錄代表性大檔與兩個並行讀取的峰值記憶體、Range／206、斷線重試、損毀檔與真實手機格式結果。

### R09 紀錄日期與歷年今日混用了 UTC 及機器本地時區

- 位置：`app/(main)/write/page.tsx:17–19`、`app/api/feed/family/route.ts:124–127`、`components/post/PostCard.tsx:37–47`。
- 新貼文 todayStr 使用 UTC 的 toISOString；回憶使用 server 本地 getMonth/getDate；貼文時間使用瀏覽器本地 getHours。程式沒有使用 APP_TIMEZONE 實作一致轉換。
- 影響：台灣凌晨 00:00–07:59 的預設紀錄日期會落到前一天；UTC 容器的回憶日期與台灣不同；外國時區裝置顯示也不符合固定台灣時間需求。
- 建議：日期字串與時間點分開處理，統一 Asia/Taipei 日期計算與 Intl 格式化；回憶只找早於當年的年份，避免目前 `!= currentYear` 將未來日期當回憶。
- 驗收：台灣午夜、UTC 容器、美國時區瀏覽器、補登、2/29 與未來日期。

### R10 三行預覽沒有原地展開收合，且會丟失文字格式

- 位置：`components/post/PostCard.tsx:219`、`:279–292`；`components/post/PostCard.module.css:128–138`。
- 卡片先 stripMarkdown，CSS clamp 三行，再以「超過 80 字或三個換行」判斷查看更多；文字只是 span，整張卡片連到詳情，沒有展開狀態或收合按鈕。
- 影響：與原先要求的「依實際三行、保留格式、原地顯示更多／收合」不同；寬螢幕可能誤顯示，窄螢幕可能裁切卻沒有提示。
- 建議：保留安全渲染的格式，以實際內容高度與 ResizeObserver 判斷，獨立按鈕設 aria-expanded，避免被整張卡片 Link 攔走。
- 驗收：320／390／768／1440px 與字級變更，短文不出按鈕，長文可原地展開並收回，粗體色彩保留。

### R11 媒體長效快取與私密區秘密儲存需收緊

- `app/api/media/[id]/route.ts:90` 使用 private,max-age=86400,immutable；`app/api/me/avatar/route.ts` 使用 public 快取。敏感媒體可能在登出或受眾變更後仍由快取直接顯示，無法再次授權；public 頭像需考慮共用代理快取。
- `app/(main)/vault/page.tsx:79,111` 將原始 PIN 放 sessionStorage，供另一頁讀取；同源腳本可讀到這個解密秘密。PIN 也會送到伺服器驗證，因此不宜宣稱伺服器從原理上無法解密所有內容。
- 建議：依媒體敏感性設 no-store／重新驗證與快取策略，登出及換帳號清理本機狀態；Vault 只在記憶體保存非匯出的金鑰，離開／逾時銷毀，避免把原始 PIN 放 Web Storage。已下載的副本仍不能撤回，需如實說明。

## 其他建議與未完成範圍

1. **補 CSRF 與受信代理邊界。** 共用 auth wrapper 沒有 Origin／CSRF 驗證；登入直接把完整 x-forwarded-for 當限速 key。SameSite=Lax 有部分保護，不能據此宣稱所有跨站情境均可攻擊，但也不應取代寫入請求驗證。對外入口應覆寫代理標頭、限制直連 app，另採帳號＋來源雙重限速。
2. **補核心寫作體驗再擴張功能。** 目前標題被前後端強制必填；工具列偏 Markdown，沒有先前的文字顏色／底線能力，卡片摘要移除格式。草稿只有手動操作，未見自動儲存／跨裝置衝突恢復；未找到真實 AI provider/API。這些應標示待完成，不能因有其他新功能就當成已交付。
3. **回憶仍是標題連結清單。** `app/(main)/family/page.tsx:133` 一帶把 memories 另做連結區塊，沒有直接用完整貼文卡呈現其媒體／原互動。建議整合為同一動態流並按 post ID 去重。保留使用者另已核定的行事曆／投票等新功能，不任意刪除。
4. **給載入失敗可操作的提示。** 家庭動態 catch 只 console.error，可能把失敗呈現成「還沒有家庭動態」；應分開空資料、未登入、讀取失敗，提供重試。
5. **同步文件與實際實作。** README 仍稱只有設計，handoff 停留 Phase 1，不能用舊 72 項認證測試代表新增功能通過。更新真實啟動、測試、備份、遷移、部署及已知限制；.env.example 補上 Compose 實際要求的 DB_PASSWORD 與容器內 db 連線範例。
6. **建立隔離驗收環境。** 獨立測試 DATABASE_URL／TEST_BASE_URL、可重建測試資料庫及確切 npm test 指令；CI 不連 NAS 正式 DB。將 P1 案例做成回歸測試，補上 lint config 後讓 CI 非互動執行。
